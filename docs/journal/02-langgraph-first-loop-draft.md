## 这次由什么决定推动

需求讨论后，我选择使用 LangGraph，并提出参考 local-deep-researcher 的反思循环。迁移到故事创作后，重点不只是反复生成，还需要创作权限、用户暂停和明确的结束条件。

因此，第一条流程是提取、审核、路由、修订或等待用户。AI 协助实现代码，我需要理解并审查模块职责、数据约定和退出边界。

## 实现中的取舍

本次使用 DeepSeek 的 JSON 输出，模型通信单独封装。提示词分为提取、创作和审核三个任务；LangGraph 负责连接节点。业务快照和流程检查点都落在本机 SQLite，但使用不同文件和职责。

项目累计最多修订三轮，默认最多十次模型请求。用户回复不会重置额度。这个限制控制调用次数，还不是金额预算。程序会在模型调用前持久记录请求，避免失败后计数丢失。

## 哪些结果可以算证据

确定性测试覆盖了模式分支、三轮退出、人工确认、重启恢复、过期恢复拒绝及伪造引用拒绝。模型替身能验证流程，不证明真实审核质量。

实际使用一个温暖写实的幼苗故事调用 DeepSeek，完成了提取和审核两次请求，返回十个创作维度，最终暂停等待用户确认。这个结果证明接入和结构化输出可用，不代表审核器有多高准确率。

## 仍然没有完成的部分

人物和道具暂时没有拆成完整的稳定实体结构；没有严格的事件状态推理，没有视频生成或 RAG。同步 HTTP 请求也还没有升级成后台队列。业务执行中突然终止的恢复，与普通人工暂停的恢复，是后续要分别处理的问题。

下一步需要真实的错误样例、正常样例和有意伏笔，用人工标注检验审核器，不能因为它能持续输出 JSON 就认为质量问题解决了。
