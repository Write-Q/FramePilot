> 本文记录最小闭环阶段，整理于 2026-09-24。此时使用 SQLite；后来的 PostgreSQL 迁移见第五篇。流程测试通过不等于审核准确率已经得到验证。

## 从需求到一条能结束的流程

[第一篇](/posts/framepilot-01-story-agent/)里，我先确定了故事创作 Agent 的目标：理解用户的输入，找出需要讨论的地方，再形成双方认可的故事。开始实现时，我选择 LangGraph，并参考了 [local-deep-researcher](https://github.com/langchain-ai/local-deep-researcher) 的循环思路。

应用到编剧场景，需要重新设计每一步的权限。审核指出问题之后，是自动改稿，还是先问用户？没有问题之后，是直接往下走，还是等待确认？这些决定不能只留在提示词里。

最小流程因此定为：

```text
输入故事 → 提取卡片 → 审核 → 程序判断
                              ├─ 允许自动修订 → 修订 → 再审核
                              └─ 等待用户 → 修改、澄清或确认
```

其中“澄清”是后续协作交互补齐的操作。最早先跑通的是修改和确认。

## 数据约定先于自由文本

用户输入需要包含故事、创作模式和明确约束。AI 输出则分为概括卡片、审核问题和修订结果，用 Pydantic 检查结构。

例如，卡片有三个容易混淆的字段：

| 字段 | 用途 |
| --- | --- |
| text | 给用户阅读的概括总结 |
| source | 标明来自原稿、用户补充、AI 建议或未知来源 |
| evidence | 支撑概括的原文引用 |

概括可以改写，证据必须能在对应材料中逐字找到。这样既允许总结，又能查到它的依据。Pydantic 负责类型和字段限制，引用是否真的存在则由业务代码另行检查。

这也形成了两层边界：JSON 能解析，并不说明字段合格；字段合格，也不说明模型的解释正确。

## 为什么拆成这些模块

| 模块 | 负责什么 |
| --- | --- |
| domain.py | 输入、输出与流程状态的数据约定 |
| workflow.py | 节点、分支、循环与人工暂停 |
| service.py | 创建项目、校验版本、恢复流程 |
| provider.py | 模型交互与响应处理 |
| storage.py | 业务状态、正文版本和调用账本 |
| main.py | HTTP 接口和页面资源 |

模型层后来接入 LangChain 的 ChatPromptTemplate 和 ChatDeepSeek；LangGraph 负责状态流转。两者分工不同。接口层不直接拼提示词，图节点也不处理 HTTP 请求。

阅读代码时可以先从接口找到入口，再沿着服务进入工作流；设计时则先考虑业务规则和数据关系。这两种顺序没有必要完全一致。

## 暂停要能恢复，调用也要计数

初期业务数据与图检查点分别放在两个 SQLite 文件里。业务库保存用户能看到的版本、状态和模型调用记录；检查点保存图执行到哪里。它们都需要持久化，职责却不同。

恢复人工暂停时，客户端必须提交当前版本号和暂停编号。服务端会核对它们，防止旧页面的修改要求作用在新版本上。原始输入与当前稿分开保存，修订不会覆盖原稿。

循环最多允许三次正文修订、十次模型请求。调用前先在账本占用额度，失败也计数，人工恢复不清零。修订前还要确认至少能支付“修订＋复审”两次请求。这里限制的是请求数，暂时没有折算金额。

## 我能从测试里得出什么

用模拟模型可以验证模式分支、次数上限、暂停恢复和伪造引用被拒绝。它不能证明真实模型判断剧情的水平。

在早期模型接入阶段，曾用一个固定的幼苗故事完成真实 DeepSeek 的提取和审核，返回十维卡片并暂停等待确认。这个结果只证明当时的连接和输出链路可用；不能当作后续 LangChain 改造及新版编剧流程已经完成真实质量评测的证据。

随后补上 SSE 流式进度，让用户看到当前阶段和生成预览。预览仍可能是不完整内容，只有完成解析和校验后的结果才是正式输出。后台可靠任务队列仍未实现。

## 这一步留下的判断

AI 协助实现代码，我需要能够说清楚这些边界：谁决定路由，谁保存版本，哪个结果经过了校验，什么时候必须停止。理解这些关系，比记住每个函数的写法更能帮助我接手项目。
