> 记录范围：2026-09-23 的迁移与验收，整理于 2026-09-24。本地迁移完成；当时 Git 提交因权限审核超时未完成，不能把本地代码与 GitHub 上的版本视为一致。

## 为什么从 SQLite 开始，又为什么换库

最小闭环阶段用 SQLite，省去了数据库服务部署，先把创作、审核和人工暂停跑通。开始重新梳理后端架构后，我决定迁到 PostgreSQL，并引入 SQLAlchemy 和 Alembic。

选择时考虑了两点：业务数据需要关系约束，卡片和状态快照又有灵活结构；后续 RAG 可以再评估 pgvector。当前没有安装向量扩展，也没有实现 RAG，不能把未来选项写成已有能力。

迁移的目标是建立清楚的数据访问和结构演进方式，保持现有业务行为，而不是只替换连接字符串。

## 两类数据都要迁

| 数据 | 新位置 | 作用 |
| --- | --- | --- |
| 项目当前状态和暂停信息 | fp_projects | 用户读取项目时的业务快照 |
| 剧本历史版本和卡片 | fp_versions | 比较、导出和追溯正文 |
| 调用状态与 token 用量 | fp_calls | 累计预算与请求记录 |
| 图检查点和待处理写入 | PostgresSaver 管理的表 | 恢复图执行和人工暂停 |

这些表位于同一个 PostgreSQL 数据库。业务层使用 SQLAlchemy，检查点使用 LangGraph 的 PostgresSaver。项目编号、额度、时间和版本号独立建列；可变的业务状态与卡片保存为 JSONB。

只迁移正文还不够。用户之前停在选方向还是确认稿，已经花了几次调用，都影响下一次请求是否正确。项目编号、检查点编号和暂停编号也需要保留。

## 配额如何避免并发超额

预占额度时，程序锁住对应项目行，在一个短事务里完成“检查已用次数”和“插入调用账本”。事务提交之后，才发起模型请求。

这样多个连接同时申请最后一次额度时，不会都读到同一个旧余额。模型请求失败仍计数，而且网络等待期间不一直占着数据库行锁。

不过，换库没有自动完成多用户改造。应用仍有进程内的操作锁，当前仍要求单进程部署。

## 旧库导入怎样保留退路

导入前先停服，确认没有运行中的任务。工具使用 SQLite backup API 生成包含已提交 WAL 内容的备份，保留原文件，再向空的 PostgreSQL 目标库导入。

业务记录和图检查点放在同一个 PostgreSQL 事务中处理。导入结束前核对检查点内容；如果缺失、冲突或校验失败，就回滚。目标库非空时直接拒绝，避免重复执行覆盖已有结果。

本次实际迁入并核对了：

- 11 个项目；
- 12 个剧本版本；
- 28 条模型调用记录；
- 60 个图检查点。

核对过程没有调用真实模型，也没有替用户确认或修改故事。

## Alembic 不能接管所有表

结构检查发现一个具体问题：业务模型里没有声明 LangGraph 的检查点表，Alembic 自动比较时会把它们当作多余表，建议删除。

修正方式是让 Alembic 的自动比较只处理 `fp_` 业务表；图表继续由 PostgresSaver 管理。这不是忽略结构差异，而是明确两套迁移工具的所有权。

修正后，Alembic 检查返回没有新的升级操作。测试还验证重复初始化不会破坏现有结构。

## 最后验收到了哪里

最终 48 项测试全部通过，使用真实 PostgreSQL 和模拟模型。覆盖原有编剧流程，以及并发额度、暂停恢复、旧库导入、缺失检查点拒绝和导入中途失败回滚。

测试过程中出现过 Windows 临时目录权限错误和 Docker 未启动导致的连接失败。它们需要先解决，再重新取得完整结果，不能把“部分测试通过”写成全部通过。Docker 的具体排障过程单独放在下一篇。

原 SQLite 与备份仍在。新版产生数据以后，不能直接退回旧库而假定没有损失；当前没有反向迁移工具。未来还有账号、后台任务和真实模型质量评测要做。
