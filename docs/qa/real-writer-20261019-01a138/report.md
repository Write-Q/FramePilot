# 真实 DeepSeek 写稿—改稿完整流程验收

日期：2026-10-19。使用当前未提交 UX 修复工作区，提示词版本 `story-v5`，配置模型 `deepseek-chat`。本轮没有更换提示词或修改业务代码来使样本通过。

## 结论

**一个真实模型样本完成了候选方向、写稿、审核、定点改稿、澄清复审、确认、导出和新应用实例读取。流程可以闭环，但过程中确实出现了引用不合格和审核误报。**

这不是首遍无失败通过：首次 compose 的卡片引用被程序拦截，人工模拟一次手动重试后获得首稿；定点改稿正确完成后，审核又误报插入位置错误，模拟用户提出事实澄清后才允许确认。不能据此宣称真实编剧质量全面合格或统计准确率。

## 实际测试方式

- 实际调用项目 DeepSeek Provider、FastAPI 流式 API、StoryService、LangGraph、PostgreSQL 业务表和检查点。
- 通过 TestClient 调用 `/api/projects/stream`、`resume/stream`、`retry/stream`、版本、差异和导出接口；本轮不是浏览器点击验收。
- 新建随机测试数据库，执行现有迁移；不改用户业务库、不读取或外发已有故事。
- 证据保存并检查完成后，仅删除本次创建的精确随机测试库，已查询确认删除；业务库保留。
- 所有创作输入为固定虚构案例；总请求上限 12 次，实际 8 次；没有生图或视频请求。
- 关闭旧应用的服务与连接后，用新的应用实例读取同一项目验证状态和调用账本一致。这是应用实例重建读取，不等同于操作系统重启或执行中崩溃恢复测试。

## 用户输入与改稿要求

标题：**雨后的小支架**。

要求：30秒写实短片；唯一人物小禾、唯一地点自家院子；主线是扶正幼苗；无对白、画外音、魔法、新人物或第二地点；结尾温暖；按4个编号镜头段落输出，时间合计30秒。

从真实生成的候选中选择“雨痕与支架”：发现倒伏、取材料、绑支架及重调、观察与微笑。其完整内容见 [创建结果](01-create.json)。

对首稿提出严格局部修改：只在第二镜头的一行末尾追加 **“小禾用指尖轻轻拢紧幼苗根部的湿土。”**，其他每个字符、段落、编号、秒数、标点与换行均保持不变。要求的原始请求与逐字预期稿保存在 [run.json](run.json)。

## 两个已确认问题

### 1. 首次写稿的来源引用不合规

模型把“主线是扶正幼苗；结尾温暖”标记为用户材料引用，但用户约束的两个分句之间还有其他文本，该字符串并不是连续原文；部分其他卡片也存在拼接引用。程序正确拒绝本次写稿，未把它保存为已通过的正式结果。

当前 `extract` 有一次带校验反馈的引用纠正，而 `compose` 没有相同的纠正流程。本次手动重试重新生成才通过。因此“引用校验保护有效”，同时“真实写稿一次成功的稳定性仍有优化空间”。

证据：[失败写稿阶段状态](02-first-draft.json)、[完整调用原始结果](run.json)。

### 2. 审核把正确的局部插入误判为违约

程序逐字检查确认：新增句直接紧接指定行最后一个句号，没有另起一行，没有其他变动。但模型声称新增句位于另一行，作为 constraint 问题交给用户，阻止确认。

之后提交“仅澄清”：说明程序比对结果、目标行原文和新句的连接位置，要求重新核对且不改稿。模型撤回问题。程序没有绕过原有审核或确认权限。

这表明逐字位置、数字等可确定的规则不宜完全交给 LLM 判断。后续可以让程序先生成明确的改动检查结果，再辅助语义审核；本轮只记录建议，没有修改实现。

证据：[修改请求及误报](03-revised.json)、[澄清后结果](04-clarified.json)、[最终确认](05-confirmed.json)。

## 用量与局限

共8次真实调用、**20,120 tokens**，模型调用耗时合计约 **23.94秒**。这不是包含数据库初始化和人工检查的端到端总耗时。未查询供应商实时账单，不估算人民币费用。

确认是验收脚本模拟用户的确认操作，不代表真实用户已经认可作品。只完成一个短片样本，未覆盖长篇风格、复杂人物关系、不同模型对比、真实生图/视频或完整质量基准。
