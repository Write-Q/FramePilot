# 编剧系统真实模型重复测试（2026-10-19）

结论：局部改写能力表现较好，但引用生成和审核的稳定性明显拖累使用体验。本批6轮仅2轮走完确认；其中1轮需额外澄清审核误报。不能把此前单轮成功视为模块已经稳定。

## 方法与边界

- 用户授权多次测试。两个固定虚构案例（扶正幼苗、给旧书包书皮）各独立运行3次，交替执行；每轮新项目，顺序运行，不挑选成功样本。
- 实际 FastAPI 流式 API、LangGraph、PostgreSQL、DeepSeek Provider。模型配置 `deepseek-chat`、temperature=0.2、提示词 `story-v5`，过程中不改代码、提示词或参数。供应商模型别名不等于已锁定底层模型快照。
- 每轮标题提取→候选首项→首稿复审→指定一行末尾追加一句，要求其余逐字保留→复审→允许时确认、导出、新应用实例读取。创建及写稿各最多一次手动重试；精准改动被阻断时最多一次事实澄清。没有对改稿失败执行额外重试。
- 预设6轮、60次模型调用上限；实际32次，全部返回可解析JSON，使用68,737 tokens，模型请求耗时合计97.8秒。无网络失败。耗时不含完整用户操作时间；未核对实际账单。
- 本批未计入此前单案例8次调用。独立数据库已在证据保存后删除，并查询确认不存在；业务库与容器卷不变。

## 可复核的问题

### 1. 引用失败反复出现，单纯重试不可靠

总计6次业务校验失败，分布于4轮：5次理解卡引用不连续或改写（写稿theme 3次、改稿actions 2次），1次审核引用不存在的原文。所有模型请求都返回JSON，HTTP正常不能算业务通过。

改稿的两个失败例中，actions.evidence 写成“本轮要求在……段末尾追加……”，这是模型概括的指令，而非用户反馈中的连续原文。程序拒绝是符合当前规则的；根本问题在于模型输出与约束不匹配，以及失败后缺少有效纠正路径。

### 2. 审核无法可靠判断修改范围

book-2 审核声称第3段“折角被压平，旧痕重新可见。”与第4段“画面停在书与手指上，温暖收束。”是越界新增。两句在该轮首稿中都已经存在，`first-draft.md`与`checks.json`可验证；修订全文实际上只追加了指定句子。事实澄清后，未改正文或正文版本，重新审核清除了该问题，随后正常确认。

这与之前单案例“新增句另起一行”的误报表现不同，但同属修改范围判断不准。不能依赖用户每次解释来挽救体验。

### 3. 短片可拍性仍需独立检验

能生成四段、合计标注30秒的文字，不证明动作能在30秒内拍完。部分段落含取材料、插支架、绕绳、打结等密集动作。当前测试没有实拍计时、分镜生成或人工盲评，也没有验证长篇、并发、多供应商和浏览器真实模型点击体验。

## 建议顺序（尚未实现）

1. 为写稿/改稿理解卡增加携带具体校验错误的有限纠正；有上限并记入调用预算，不能无条件放宽引用规则。
2. 局部编辑使用确定性的文本差异检查，并向审核提供上一稿、当前稿与差异。把程序已经证明的字符变化与模型判断的剧情冲突分开处理。
3. 改稿失败时明确提示“新稿未采用，当前仍为旧稿”，并提供有效重试入口；让失败后的恢复路径可见。
4. 修复后复跑这6例同协议，比较首次成功、恢复成本、误报和调用消耗；再扩大题材与长短，不以增加样本替代修复。

## 证据与复现

- `run.json`：全部32次请求的业务输入、模型原始JSON、tokens、阶段API结果与失败；只含虚构案例，无API密钥或连接口令。
- `checks.json`：逐轮指标、错误、正文精确比较与误报证据。
- 子目录：首稿、保存的最终正文、差异、导出、各阶段JSON。未进入改稿的轮次没有伪造后续产物。
- `reproduce.py`：本批探针源代码。需项目环境、真实模型密钥与本地PostgreSQL；再次执行前将ROOT改为全新目录，脚本拒绝覆盖已有证据。真实调用会产生用量。
- 本轮没有改产品代码或提示词，没有提交、合并或推送。已有其他任务修改保持原状。
